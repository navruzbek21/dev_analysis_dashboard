Что видно с площадки

Ключ кэша — это версия данных плюс версия кода

Каждый ключ собирается как prefix:namespace:sha256(payload), где payload всегда содержит dataset_version и code_version. Первое — строка вида parquet:df2.parquet:<mtime>:<size>|…, поэтому подмена файла на диске обесценивает все ключи сама, без рестарта и без ручной чистки.

Второе — переменная окружения CODE_CACHE_VERSION. Поверх этого каждое пространство имён несёт собственную версию алгоритма: asset-year-v4-weighted, wc-kiz-dp-linear-sse-v2-block, plotly-figure-cache-v1. Меняется семантика расчёта — двигается только своя ветка кэша.

L1 живёт в воркере, а воркеров два

local_cache — это TTLCache на уровне модуля, то есть по одному экземпляру на процесс. Контейнер поднимает gunicorn с --workers 2, значит L1-кэшей физически два, и они не знают друг о друге: один и тот же срез может быть посчитан дважды, по разу на воркер.

Общий тир ровно один — Redis. Он же и снимает дубль работы: тяжёлые загрузчики берут распределённую блокировку key:lock, поэтому параллельный расчёт одного среза схлопывается в один.

LLM выбирает инструмент, но не касается данных

В режиме анализа модель вызывается дважды и оба раза мимо данных. Первый вызов возвращает JSON вида {"tool":…,"params":…}; _normalize_plan прижимает tool к списку ALLOWED_TOOLS из шести имён, а метрику — к ALLOWED_METRICS. Всё, что не прошло, молча становится metric_dynamics.

Считает затем обычный pandas по parquet. Второй вызов модели получает уже готовый результат — не более 30 строк — и пишет по нему текст. Промпт прямо запрещает SQL, а на случай недоступного шлюза рядом лежит правиловый план и детерминированное объяснение.

analytics_tools.py:36 · analytics_tools.py:210 · analytics_tools.py:232 · litellm_console.py:221

Токен уходит наружу и не откатывается на слабый TLS

Прокси ходит на litellm.tatneft.guru под серверным токеном из LITELLM_API_KEY — пользовательский токен в схеме не участвует вовсе. При провале проверки сертификата код не пытается переподключиться без верификации: он возвращает ошибку и предлагает указать корпоративный CA через LITELLM_CA_BUNDLE.

Периметр держат три ограничителя: лимит 20 запросов за 60 с по X-Forwarded-For, потолки 32 000 символов на запрос и 40 сообщений в истории, и белый список моделей. Лимитер — тоже in-memory, то есть на воркер, и с двумя воркерами фактический потолок вдвое выше номинала.

Тема накладывается после кэша, а не до

Колбэки кладут в кэш «сырые», нетемизированные фигуры, и лишь потом накрывают их apply_runtime_theme(fig, theme). Поэтому переключение светлой и тёмной темы не пересчитывает ни один график: все четыре фигуры главной вкладки и шесть фигур вкладки актива приходят из L1 или Redis, а тема стоит поверх дёшево.

Консоль LiteLLM живёт в отдельном документе внутри iframe и о смене темы узнаёт через clientside-колбэк с postMessage, а не опросом localStorage по таймеру.

Один parquet читают два независимых загрузчика

df_ploshad_year.parquet открывают и data_service._load_parquet_year_data, и gtm_analysis._load_gtm_dataset — каждый со своим lru_cache, своей сигнатурой файла и своей нормализацией. В памяти воркера это два разных кадра из одного файла.

Слой анализа добавляет третий путь: analytics_tools._read_parquet_cached читает месячный и годовой parquet напрямую, в обход сервисов, для таблиц monthly_raw и yearly_raw. Сервисный слой такие срезы не видит и не кэширует.
